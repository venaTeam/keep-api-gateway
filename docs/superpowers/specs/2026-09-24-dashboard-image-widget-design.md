# Dashboard Image Widget — Design

- **Date:** 2026-09-24
- **Status:** Approved in brainstorming, pending written-spec review
- **Repos:** keep-migrations, keep-api-gateway, keep-ui (branch `feat/dashboard-image-widget` off `origin/dev` in each; local only)
- **Not affected:** keep-event-handler, keep-workflows (neither reads nor writes dashboards)

## 1. Goal

Add a dashboard panel type that renders a picture (PNG, JPEG, GIF, WEBP, SVG). Users either paste an image URL or upload a file. Uploaded images are stored in Keep's own database, so the feature works in the air-gapped production environment without any new infrastructure.

### Decisions made during brainstorming

| Topic | Decision |
|---|---|
| Image source | Both: **URL** or **upload** |
| Upload storage | New `dashboardimage` table in the existing Postgres (`bytea`), following the `providerimage` pattern. Not inline in `dashboard_config`, not reusing the provider-image endpoints (hard-coded `-icon.png`/`image/png`, provider scopes, name collisions, fallback-instead-of-404) |
| Display options (v1) | Fit mode (`contain` default / `cover`) and optional click-through link |
| Size cap | `KEEP_DASHBOARD_IMAGE_MAX_BYTES`, default 5 MB, enforced in the gateway (the OpenShift Route imposes no body limit, so this is the only guard) |
| Lifecycle | Two-phase: upload creates a *pending* image; a dashboard save *claims* it in the same transaction and rejects any bad reference |
| Pending cap | `KEEP_DASHBOARD_IMAGE_MAX_PENDING`, default 20 per tenant |
| Per-tenant total-bytes cap | Not added |
| Migration | One new table; no backfill |

### Out of scope (v1)

- Update endpoint (a replacement is a new upload), list/gallery endpoint, sharing one image between dashboards (a claimed image belongs to exactly one dashboard; copying requires re-upload)
- Hide-title and background-colour display options
- Server-side proxying of URL images (URL images load directly in the viewer's browser)

## 2. Data model and migration (keep-migrations)

New hand-written revision `migrations/versions/2026-09-24-00-00_add_dashboard_image.py`:

- `revision = "add_dashboard_image"`, `down_revision = "derive_alert_suppression"` (the single head on `dev` at `696cce4`)
- Table declared locally; no model imports (repo rule 2)

**Upgrade** creates table `dashboardimage`:

| Column | Type | Constraints |
|---|---|---|
| `id` | string | primary key (UUID4 generated by the gateway) |
| `tenant_id` | string | not null, FK → `tenant.id`, indexed |
| `dashboard_id` | string | **nullable** (NULL = pending), FK → `dashboard.id` `ON DELETE CASCADE`, indexed |
| `name` | string | not null (original filename) |
| `content_type` | string | not null |
| `size_bytes` | integer | not null |
| `image_blob` | `LargeBinary` with `mysql.LONGBLOB` variant | not null |
| `created_by` | string | nullable |
| `created_at` | timestamp | not null |

**Downgrade** drops the table (and its indexes). `keep-migrate --check` refuses this path without `--allow-destructive`, as intended.

**No backfill:** the table is new and no existing dashboard references an image.

**Rollout:** the migration runs as the Argo PreSync Job before new gateway pods start; the new gateway's `/readyz` requires the table. Rolling the gateway back is safe (older images ignore extra tables).

## 3. Gateway (keep-api-gateway)

### 3.1 Model and config

- `src/models/db/dashboard_image.py`: `DashboardImage(SQLModel, table=True)` matching §2; registered in `src/models/db/all_models.py` so `schema_drift()` and `/readyz` cover it.
- `src/config/config.py`:
  - `KEEP_DASHBOARD_IMAGE_MAX_BYTES` (int, default `5_242_880`)
  - `KEEP_DASHBOARD_IMAGE_MAX_PENDING` (int, default `20`)
  - Pending grace period is a module constant: 24 hours.

### 3.2 Endpoints — `src/routes/dashboard_images.py`, mounted at `/dashboard-images`

The router takes its session from `get_session` in `src/repositories/db.py` (the engine patched by the test conftest). It must not create its own engine.

**`POST /dashboard-images`** (scope `write:dashboards`, multipart field `file`)

Checks, in order:
1. `Content-Length` header present and > max → `413`.
2. Declared content type not in {`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `image/svg+xml`} → `415`.
3. Read the body in chunks; exceeding max → `413` (the header can be absent or false). Empty → `400`. Malformed/truncated multipart → `400` (framework).
4. Content must match the declared type:
   - PNG starts with `\x89PNG\r\n\x1a\n`
   - JPEG starts with `FF D8 FF`
   - GIF starts with `GIF87a`/`GIF89a`
   - WEBP has `RIFF` at 0 and `WEBP` at 8
   - SVG: reject if it contains `<!DOCTYPE` or `<!ENTITY`; must parse with `xml.etree.ElementTree.fromstring` and the root tag's local name must be `svg`

   Mismatch → `415`.
5. Sweep: delete this tenant's pending images (`dashboard_id IS NULL`) with `created_at` older than 24 h.
6. Pending cap: if the tenant already has `KEEP_DASHBOARD_IMAGE_MAX_PENDING` pending images → `429`.
7. Insert the pending row and return `201 {id, name, content_type, size_bytes}`.

**`GET /dashboard-images/{id}`** (scope `read:dashboards`)
- Row not found, or found for another tenant → `404` (no fallback image).
- Pending images are fetchable (the unsaved widget needs to render them).
- Response: the bytes with the stored `Content-Type` and these headers:
  - `X-Content-Type-Options: nosniff`
  - `Content-Security-Policy: sandbox`
  - `Cache-Control: private, max-age=31536000, immutable`

### 3.3 Claim step in the dashboard write path

Dashboards have a single write path: `create_dashboard`, `update_dashboard` and `delete_dashboard` in `src/repositories/db.py`. Claim helpers live in `src/repositories/dashboard_images.py` and operate on the caller's session, so they share its transaction.

**Referenced ids** are every `imageId` in `dashboard_config["widget_data"]` whose widget has `widgetType == "IMAGE"` and `image.source == "upload"`.

**On create/update**, before commit:
1. Load the referenced rows by id, filtered by `tenant_id`.
2. An id is invalid if it has no row, or its row is attached to a *different* dashboard. If any id is invalid, raise `DashboardImageReferenceError(invalid_ids)`. Nothing is written.
3. Set `dashboard_id` on the referenced pending rows.
4. Delete rows with `dashboard_id == this dashboard` whose id is not referenced (the widget was removed or its image replaced).
5. Commit together with the dashboard change.

For create, the dashboard row is flushed first so its id exists for step 3.

The routes in `src/routes/dashboard.py` catch `DashboardImageReferenceError` and return `400 {"message": "Dashboard references missing or unavailable images", "invalid_image_ids": [...]}`.

**On delete:** delete the dashboard's images explicitly in the same session before deleting the dashboard. The explicit delete keeps behaviour correct on engines that don't enforce FK cascades (SQLite in tests); the FK `ON DELETE CASCADE` is only a backstop.

**Compatibility:** existing dashboards contain no image references, so every current save behaves exactly as before. `400` is only possible when an `IMAGE` widget references a bad upload.

### 3.4 Performance envelope

- **Dashboard list/fetch:** unchanged. Blobs are never in `dashboard_config`, and there is no join.
- **Image fetch:** a primary-key lookup, independent of table size. Browsers cache responses immutably.
- **Save:** three indexed queries whose cost scales with the widgets of the dashboard being saved.
- **Upload:** sweep and count touch at most 20 pending rows per tenant.
- **Long-run cost:** Postgres storage only, bounded by live image widgets plus 20 pending per tenant (no orphans).

## 4. UI (keep-ui)

### 4.1 Data shape (stored in `dashboard_config`)

```ts
export enum WidgetType { /* existing */ IMAGE = "IMAGE" }

export type ImageFit = "contain" | "cover";

export interface ImageWidgetConfig {
  source: "upload" | "url";
  imageId?: string;
  url?: string;
  fit: ImageFit;
  link?: string;
}

export interface WidgetData extends LayoutItem {
  // existing fields…
  image?: ImageWidgetConfig;
}
```

### 4.2 New files

**`src/entities/dashboard-images/model/useDashboardImages.ts`**
- `uploadDashboardImage(api, file)`: `FormData` POST via `api.request` (same as the provider-image uploader); returns `{id, name, content_type, size_bytes}`.
- `useDashboardImage(imageId)`: fetches the image with the Bearer token through SWR, returns a blob URL, and revokes it on unmount. Mirrors `entities/provider-images/model/useProviderImages.ts`.

**`src/app/(keep)/dashboard/widget-types/image/image-widget-form.tsx`**
- **Source toggle:** Upload / URL.
- **Upload:**
  - accepts `.png,.jpg,.jpeg,.gif,.webp,.svg`
  - checks type and size on the client (the limit is shown)
  - uploads as soon as a file is picked, with a spinner and preview
  - the form is valid only once an `imageId` is returned
  - errors are shown inline with a retry
- **URL:** required; must be `http://` or `https://`.
- **Fit:** `contain` (default) / `cover`.
- **Link (optional):** must be `http://` or `https://`.
- **Default layout for new widgets:** `w: 4, h: 4, minW: 0, minH: 2`.

**`src/app/(keep)/dashboard/widget-types/image/image-grid-item.tsx`**
- Renders an `<img>` filling the card with `object-fit` from `fit`. The source is the blob URL for uploads and `url` for URLs; `alt` is the widget name.
- When `link` is set, the image is wrapped in `<a href target="_blank" rel="noopener noreferrer">`.
- Shows a skeleton while loading.
- A fetch error, `404` or `<img onError>` shows a muted "Image unavailable" placeholder inside the card.

### 4.3 Edits

- `WidgetModal.tsx`: an "Image" option in the type select; renders `ImageWidgetForm`.
- `GridItem.tsx`: renders `ImageGridItem` when `item.widgetType === WidgetType.IMAGE`.
- `[id]/dashboard.tsx` `handleSaveDashboard`: when a save returns `400` with `invalid_image_ids`, the toast names the affected widgets. The existing `showErrorToast` path is kept for other errors.

## 5. Error handling

| Situation | Gateway | UI |
|---|---|---|
| Unsupported type / content mismatch | `415` | form error "Unsupported or corrupt image (PNG, JPEG, GIF, WEBP, SVG)" |
| Over size cap | `413` | caught client-side first; gateway is the backstop |
| Empty / truncated upload | `400` | form error + retry |
| Pending cap reached | `429` | "Too many unsaved images — save or discard the dashboard first" |
| Save references a bad image | `400` + `invalid_image_ids`, nothing written | toast naming the widgets; dashboard stays editable |
| Image fetch fails / 404 / URL fails to load | — | "Image unavailable" placeholder in the card only |

## 6. Security

- Tenant isolation: every query is filtered by `tenant_id`; a cross-tenant id returns `404` on fetch and `400` on save.
- Scopes: `read:dashboards` / `write:dashboards`, matching the existing dashboard routes.
- SVG is only displayed via `<img>` (scripts never execute). Direct navigation to the image URL is neutralised by `CSP: sandbox` and `nosniff`. DOCTYPE/ENTITY declarations are rejected at upload.
- URL and link fields accept only `http(s)`, which blocks `javascript:` and `data:`.
- Size and pending caps bound memory per request and storage growth per tenant.

## 7. Testing

**keep-migrations** (following the existing `tests/test_*_migration.py` pattern)
- Upgrade creates the table, columns, indexes and FKs.
- Downgrade drops it.
- `--check` refuses the downgrade path.

**keep-api-gateway** (pytest)
- Upload:
  - `201` for each of the five types
  - `415` for a disallowed type, byte mismatch, and SVG with DOCTYPE/ENTITY or a non-`svg` root
  - `413` via `Content-Length` and via an oversized body with no/false header
  - `400` for an empty file
  - `429` at the pending cap
  - the sweep deletes only this tenant's pending rows older than 24 h
- Fetch:
  - the correct `Content-Type` and the three headers
  - `404` for an unknown id and for another tenant's id
- Dashboard create/update:
  - claims pending images
  - `400` with no write for an unknown, cross-tenant or other-dashboard id
  - deletes images that are no longer referenced
  - dashboards without image widgets are unchanged
- Dashboard delete removes its images.
- `schema_drift()` passes with the new model.

**keep-ui**
- Jest: form validation (URL scheme, type/size, submit disabled until upload completes) and the grid item's placeholder on error.
- `npm run typecheck` and `npm run lint` (the build ignores both).

**End to end**
- `/sanity-check` (dashboard checks).
- Manual: upload a PNG and an SVG, add a URL image with a link, save, reload, then delete a widget, save, and confirm its row is gone. Also delete the dashboard and confirm all its images are gone.
